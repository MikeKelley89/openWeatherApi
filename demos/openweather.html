REQUEST ARCHITECTURE

The browser never receives the provider key

The browser sends only the ZIP code to a narrowly scoped Cloudflare Worker. The Worker validates the request, applies a rate limit, calls OpenWeather with a server-side secret, and returns only the data the interface needs.

1. BrowserValidate ZIP; request /weather?zip=84010
→
2. Cloudflare WorkerCheck origin, method, input, and rate limit
→
3. OpenWeatherGeocode ZIP, then retrieve forecast

Secret boundary: OPENWEATHER_API_KEY is configured in Cloudflare Worker Secrets. It is not embedded in this page or sent to the browser.

The Worker source and setup documentation describe the server-side request handling and configuration.

Architecture overview

The browser does not call OpenWeather directly. It sends the ZIP code to a Cloudflare Worker, which makes two requests to OpenWeather:

  • Geocoding API - Resolves a supported location or ZIP code to latitude and longitude coordinates.
  • One Call API 3.0 - Returns weather data for a location specified by latitude and longitude. Accepting a ZIP code in the interface avoids requiring users to supply geographic coordinates.

The browser sends a five-digit US ZIP code to the Worker. The Worker asks the Geocoding API for latitude and longitude, passes those coordinates to One Call API 3.0, and returns a small JSON response for the page to render. This keeps the provider credential on the server while keeping the browser code simple.

The interface accepts five-digit US ZIP codes. ZIP+4 values are outside the scope of this example.

Client request flow

The client uses jQuery to handle form submission, send an asynchronous request to the Worker, and update the interface. The main steps are outlined below. Code samples are simplified excerpts intended to illustrate the request flow.

  1. Validate the ZIP code as the user edits the field. The client enables submission only when the value contains exactly five digits. The Worker repeats this validation because client-side checks can be bypassed. 

    
function validZip(value) {
  return /^\d{5}$/.test(value);
}

$zip.on("input", function () {
  const zip = this.value.trim();
  const valid = validZip(zip);

  $button.prop("disabled", !valid);
  $("#zipStatus").toggle(!valid);

  if (!valid) clearWeather();
});

  2. Intercept form submission, validate again, clear any previous results, and disable the button while the request is in progress. 

    
$form.on("submit", function (event) {
  event.preventDefault();
  const zip = $zip.val().trim();

  if (!validZip(zip)) {
    $("#zipStatus").show();
    return;
  }

  clearWeather();
  $button.prop("disabled", true);

  // The asynchronous request follows.
});

  3. Send one GET request to the Worker. The ZIP code is a query parameter; the browser does not call OpenWeather directly and does not receive the API key. 

    
$.ajax({
  url: weatherEndpoint,
  method: "GET",
  data: { zip: zip },
  dataType: "json",
  timeout: 12000
}).done(function (payload) {
  // Render the returned location and weather data.
}).fail(function (xhr, textStatus) {
  // Display a safe error message.
}).always(function () {
  $button.prop("disabled", !validZip($zip.val().trim()));

  4. The Worker validates the request and calls the Geocoding API, then One Call API 3.0. It returns a reduced response with a location object and a weather object. This excerpt shows the successful response shape. 

    
// Cloudflare Worker: response payload
return jsonResponse({

  5. Read the response using the same property paths returned by the Worker. The client checks optional fields before displaying them and inserts values with .text(), rather than interpreting API data as HTML. 

    
const location = payload.location || {};
const weather = payload.weather || {};
const current = weather.current || {};
const daily = (weather.daily && weather.daily[0]) || {};
const currentCondition = (current.weather && current.weather[0]) || {};

$("#conditions").text(
  "Conditions for " + (location.name || "Selected location") +
  ", " + (location.country || "US") + "..."
);
$("#main_temp").text(
  Number.isFinite(current.temp) ? Math.round(current.temp) : "Unavailable"
);
$("#wind_speed").text(
  Number.isFinite(current.wind_speed) ? current.wind_speed : "Unavailable"
);
$("#wind_direction").text(
  Number.isFinite(current.wind_deg) ? current.wind_deg : "Unavailable"
);
$("#weather_conditions").text(
  (daily.summary ? daily.summary + " " : "") +
  (currentCondition.description
    ? "Currently: " + currentCondition.description + "."
    : "Current conditions are unavailable.")
);

  6. If the response includes weather alerts, the client displays the first alert. The API returns alert timestamps in Unix seconds, so the client multiplies them by 1,000 before creating JavaScript Date objects. Missing alert fields receive fallback text. 

    
const alerts = Array.isArray(weather.alerts) ? weather.alerts : [];
if (alerts.length) {
  const alert = alerts[0];

  $("#sender_name").text(alert.sender_name || "Weather service");
  $("#event").text(alert.event || "Weather alert");
  $("#start").text(
    alert.start ? new Date(alert.start * 1000).toLocaleString() : "Not provided"
  );
  $("#end").text(
    alert.end ? new Date(alert.end * 1000).toLocaleString() : "Not provided"
  );
  $("#description").text(alert.description || "No description provided.");
  $("#tags").text(
    Array.isArray(alert.tags) ? alert.tags.join(", ") : "Not provided"
  );
  $alert.show();
}

  7. On failure, the client reads the Worker's structured error.message when available. Otherwise, it uses a generic message, with a separate timeout explanation. The Worker maps upstream errors to safe messages rather than forwarding provider response bodies. 

    
function showError(xhr, fallback) {
  const payload = xhr.responseJSON || {};
  const message = payload.error && payload.error.message
    ? payload.error.message
    : fallback;

  $("#errorCode").text(xhr.status ? xhr.status + ": " : "");
  $("#errorMsg").text(message);
  $apiError.show();
}

.fail(function (xhr, textStatus) {
  showError(
    xhr,
    textStatus === "timeout"
      ? "The request timed out. Please try again."
      : "The weather service could not complete the lookup."
  );
});

Limitations and potential improvements

This is a focused portfolio application, not a production weather service. Its purpose is to demonstrate API integration and to document the reasoning behind the implementation. Reviewing the limitations also identifies the work required to make the application more robust.

Application limitations

The current implementation has several known areas for improvement:

  • Client-side validation improves feedback but is not a security boundary. The Worker independently validates the incoming ZIP code, so malformed requests are not accepted simply because they bypass the browser interface. Automated tests would help verify form behavior for keyboard submission and invalid input.

  • The ZIP validator checks format, not whether the ZIP code maps to a valid location. The Geocoding API provides the next validation step by determining whether the location can be resolved.

  • The API can return multiple alerts for a location, each with a different event, time window, and description.

    The interface currently displays only the first item in the returned alerts array. A more complete implementation would render each alert separately and ensure that users can distinguish overlapping or concurrent events.

  • The original version placed the OpenWeather key in browser-side JavaScript, which made it visible to every visitor. I replaced that design with a Cloudflare Worker proxy and a server-side OPENWEATHER_API_KEY secret. The client sends only a ZIP code; the Worker accepts only the expected endpoint and method, validates input, applies an approximate rate limit, and returns sanitized errors instead of raw provider responses.

    This reduces credential exposure, but it does not make the public endpoint private. CORS is a browser control, not authentication, and the rate limit is approximate. Provider-side usage limits and monitoring should remain enabled. See the Worker setup guide for deployment and testing instructions.

AI-assisted development

Using AI as part of the engineering workflow

I wrote the original HTML, CSS, and JavaScript for this demo. When I identified that the OpenWeather API key was exposed in browser-side code, I used ChatGPT to help analyze the security problem and design a Cloudflare Worker proxy so the key could be stored as a server-side secret instead.

Prompting AI toward a concrete engineering solution

I used the existing repository, its code, and the intended request flow as context, then directed the AI-assisted work toward a specific goal: keep the key out of the browser while preserving the demo's behavior. The resulting Worker validates ZIP-code input, applies CORS restrictions and an approximate rate limit when configured, handles upstream timeouts and failures, and returns a reduced response with safe error messages.

Applying changes to the original project

After working through the Worker implementation, I used AI tooling to modify the existing project directly: updating the client to call the Worker, bringing the walkthrough examples into line with the implementation, revising setup documentation, and committing the changes to GitHub. This was an applied workflow across problem analysis, prompting, code changes, documentation, and version control, not a standalone AI-generated sample.

Human direction and review

My contribution was to identify the problem, supply relevant project context, specify the intended behavior, guide the changes, and check consistency between the code and its explanation. AI helped accelerate implementation, but generated changes still need human review and testing. I treat it as a development tool, not as a substitute for engineering judgment.

This implementation reduces exposure of the API credential; it does not make a public endpoint private. CORS is not authentication, and the rate limiter is approximate.
